# Java 后端代码审查

## 明确审查范围
按用户指定的文件、提交、分支差异或 PR 审查。未指定范围时，先检查 Git 状态和现有差异；仅在无法确定审查对象时询问。
保留用户已有修改。审查请求默认只读；修复、提交或发布须在用户任务授权范围内进行。

## 跟踪实际行为
阅读变更和直接相关的调用方、数据结构、配置及测试，确认输入如何到达风险点。
只在相应逻辑存在时读取 [references/backend-risks.md](references/backend-risks.md) 对应条目，不机械罗列全部风险。
优先寻找会导致越权、数据错误、事务失效、并发异常或行为回归的问题。

## 建立证据
每项发现必须说明具体触发条件、实际后果及文件行号；必要时给最小复现或有针对性的测试。
区分可确认缺陷与依赖运行环境的推测。证据不足时注明待验证前提，不将猜测写成已确认 Bug。
避免运行生产写操作或无关的全量测试。报告实际执行的检查及未覆盖的部分。

## 交付审查结果
按影响程度排序，使用以下格式：
- [P1/P2/P3] 简短标题
- 位置：文件与行号
- 触发条件与后果
- 证据及最小修复方向

P1 表示高影响的数据、安全或主要功能问题；P2 表示需要修复的普通功能缺陷；P3 表示较低影响问题。按具体影响定级。
发现优先，背景概述从简。没有发现时明确说明审查范围和测试限制，不为凑数量输出样式建议。
