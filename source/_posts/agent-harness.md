一个大模型能写代码，不代表它能独立完成一个软件项目。

让它修一个函数，可能只需要几轮对话；让它持续开发、运行测试、处理异常并跨会话继续工作，就会遇到另一类问题：它会忘记做到哪里，工具会超时，环境可能被改坏，也可能没有充分验证就宣布任务完成。

解决这些问题，除了模型能力，还需要模型周围的工程系统。这就是本文讨论的 **Agent Harness**。

## 1. Harness 到底是什么？

Harness 原意有“挽具、约束装置”等含义。在软件领域，也能指运行和测试某个组件的支撑环境，例如 Test Harness。

本文讨论的是 AI Agent 语境中的 Harness，不是同名的持续交付平台。这个术语目前没有完全统一的边界，不同团队可能把 SDK、运行时或一套完整的 Agent 执行环境称为 Harness。

可以用下面的定义理解它：

> Agent Harness 是围绕模型搭建的执行与控制系统，负责组织模型调用、工具执行、任务状态、上下文、权限和反馈，让任务能够在明确边界内持续推进。

它不是另一个大模型，而是让模型能够有效工作的“周边系统”。

拿一个简化的类比来说：模型像一位会分析问题的开发者，工具像终端、编辑器和数据库，Harness 则提供工作环境、任务记录、操作权限、交接机制和验收流程。

这个类比有局限：模型没有人类那样持续存在的工作记忆，不能因为它表现得像开发者，就默认它会主动遵守所有工程纪律。

## 2. Model、Agent、Harness 与 Framework 的关系

这些词经常出现在同一段讨论中，但侧重点不同。

| 概念 | 主要回答的问题 | 例子 |
| --- | --- | --- |
| Model | 如何理解输入并产生下一步输出？ | 生成回答或工具调用 |
| Agent | 如何围绕目标自主选择行动？ | 根据报错决定阅读代码、修改文件、重新测试 |
| Harness | 如何让行动循环可执行、可恢复、可控制？ | 调度工具、保存状态、限制权限、记录验证结果 |
| Framework / SDK | 用什么开发组件搭建系统？ | 消息抽象、工具注册、工作流和会话接口 |

Agent 可以视为模型与 Harness 共同作用后形成的目标导向系统；具体产品中的命名可能有所重叠。

Framework 提供搭建系统的材料，Harness 更关注这些材料组合后实际怎样运行。使用某个框架，并不自动意味着权限、状态恢复和评估问题已经解决。

另外，**Agent Harness 与 Evaluation Harness 也不完全相同**：前者侧重运行任务，后者侧重在统一条件下评测模型或系统。两者可以结合，但不应混用。

## 3. 为什么一段 Prompt 不够？

假设给模型一个目标：

> 为现有 Java 项目增加订单查询接口，并完成测试。

Prompt 可以告诉它业务需求和编码风格，但仍然无法单独解决下面的问题：

- 模型要求读取文件时，谁真正执行读取？
- 调用测试命令超时后，怎样记录和处理？
- 历史日志太长时，哪些信息应该保留？
- 进程中断后，如何恢复当前任务？
- 模型提出删除文件或发布服务时，谁检查权限？
- 模型说“完成了”，怎样确认接口实际可用？

这些问题需要程序、持久化存储、执行环境和验证机制来处理。

尤其要区分两件事：**Prompt 可以要求模型遵守规则，Harness 必须在执行层落实必要的限制。**“请不要修改生产数据库”不能替代只读账号和数据库权限配置。

## 4. Harness 的核心组成

下面是一种工程拆解方式，不是所有产品都必须包含相同模块。

### 4.1 执行循环：把输出变成下一步行动

常见循环可以表示为：

~~~text
目标与当前状态
       |
       v
整理上下文 -> 调用模型
                 |
                 v
         判断结束 / 请求工具
                 |
                 v
         参数校验与权限检查
                 |
                 v
             执行工具
                 |
                 v
        保存结果、更新任务状态
                 |
                 +----> 下一轮
~~~

模型负责提出行动，Harness 负责解析请求、实际执行，并将结果带回下一轮。

循环必须有停止条件：任务完成、用户取消、预算耗尽、超时、连续失败或需要人工决策。否则系统可能一直重复尝试。

### 4.2 工具契约与执行环境

工具不是随便暴露一个函数就够了。一个可靠的工具应该明确：

- 输入参数、必填字段和允许范围。
- 返回结构、错误类型和执行状态。
- 超时、取消及有限重试策略。
- 是否有副作用，是否支持幂等。
- 工具实际能访问哪些文件、服务和网络资源。

以订单系统为例，查询订单失败可以尝试有限重试；创建退款失败却不能直接重复执行，因为第一次请求可能已经成功，只是响应没有返回。

对于有副作用的操作，应结合业务幂等键、执行记录和状态查询来处理。Agent 的调用记录不等于业务系统中的“恰好执行一次”。

### 4.3 上下文工程：每轮让模型看到什么？

长任务会产生大量对话、日志和中间结果。把所有信息不断追加到 Prompt 中，会增加成本，也可能让重要内容被噪声淹没。

Anthropic 的上下文工程文章强调：上下文是有限资源，需要持续筛选和维护。[2]

Harness 可以采用这些策略：

- 优先保留目标、约束、关键决策和待解决问题。
- 对冗长工具输出做摘要，保存原始结果的路径。
- 按需读取相关文件，避免一次塞入整个仓库。
- 压缩历史对话，但保留可核对的证据引用。
- 将任务状态写入外部存储，在后续会话中重新加载。

压缩不是无损操作。摘要可能漏掉细节，所以测试结果、文件变更、任务清单等关键事实，最好拥有独立记录。

### 4.4 状态与记忆：让任务可以交接

状态不仅是聊天记录，还包括：

- 当前目标和验收条件。
- 已完成、待完成和被阻塞的工作。
- 修改过的文件及对应版本。
- 已执行的工具请求和结果。
- 当前预算、授权及待审批动作。

短任务可以使用内存状态；长任务通常需要持久化记录。

要注意，保存了 checkpoint 不代表外部操作可以自动回滚。恢复时还必须核对文件、数据库和远端服务的真实状态，特别是“操作已执行，但结果尚未写入记录”的情况。

### 4.5 权限控制：自主行动也需要边界

权限不应只存在于提示词里。

可以按场景配置只读数据源、限定工作目录、隔离执行环境和允许使用的工具。有副作用的动作，还需要业务授权、参数校验及审计。

“需要审批”也不意味着每一步都必须打断用户。如果用户已经明确授权了某项操作，系统应在该范围内继续执行；只有超出授权或需要关键决策时才请求确认。

网页、邮件和工具返回内容应作为数据处理，不能因为其中出现“忽略之前的规则”，就变成更高优先级的执行指令。

### 4.6 验证与可观测性：不要只相信“我完成了”

验证应与任务目标对应：

| 任务 | 可以检查的证据 |
| --- | --- |
| 修改代码 | 差异、相关测试、构建结果 |
| 增加接口 | 正常与异常请求结果、权限测试 |
| 发布文章 | 生成页面、部署结果、线上访问 |
| 研究资料 | 引用来源、事实核对、结论与证据的对应关系 |

模型自我检查可以辅助验证，但不能完全替代独立的测试和约束。

同时，Harness 应记录任务 ID、模型调用、工具执行耗时、错误、预算和验收结果。日志需要脱敏；为了追踪行为而保存所有原始上下文，可能引入额外的数据泄露风险。

## 5. 长时间运行：比“压缩对话”更进一步

Anthropic 在《Effective harnesses for long-running agents》中讨论了两个典型问题：[1]

第一，Agent 想一次做太多，最终留下半完成的实现和不清楚的交接记录。

第二，后续会话看到项目已有一些功能，就过早判断整个任务完成。

他们在一个 Web 开发实验中采用了这样的方案：

1. 第一个会话负责初始化环境、功能清单、进度文件和 Git 基线。
2. 后续会话先阅读进度和提交记录，检查基本功能，再选择一个未完成的功能。
3. 每次只推进有限范围的工作，并留下清晰的变更和交接记录。
4. 功能经过验证后，才将对应条目标记为通过。

核心思路是：**把连续工作所需的信息变成可读取的产物，而不是寄希望于模型记住所有历史。**

这不是所有任务的唯一最佳架构。该文章讨论的是特定 Web 开发实验，也明确指出如何泛化到其他领域仍需探索。

## 6. 一个后端研发场景

下面是设计示例，不是已经上线的项目成果。

目标：为订单服务增加按用户分页查询接口，并验证访问控制。

一个简单 Harness 可以保存这些内容：

~~~text
task.json       目标、约束、验收条件、当前阶段
progress.md     已完成工作、关键决策、下一步
artifacts/      构建日志、测试结果、接口验证记录
Git             文件变更与可追踪的版本
~~~

执行过程可以是：

1. 阅读项目结构和现有鉴权逻辑。
2. 明确分页上限，以及用户只能查询自己的订单。
3. 实现查询接口和相关测试。
4. 运行构建，检查正常查询、空结果、越权请求。
5. 保存验证证据，更新任务状态。
6. 如需发布，再根据当前授权执行发布流程。

如果构建失败，工具应返回退出码和错误摘要，模型根据结果修复。如果当前会话即将结束，就保存剩余问题；下一次先核对状态，再继续工作。

这样，Harness 不替代业务设计，却能减少“实现了部分代码，却误以为整个需求已经交付”的情况。

## 7. 一个最小执行循环

下面是概念性 Python 伪代码，不是可直接用于生产的实现：

~~~python
state = restore_or_create_task()
status = "budget_exhausted"

for _ in range(max_steps):
    if state.cancelled or budget.exhausted():
        status = "stopped"
        break

    context = build_context(state)
    decision = model.next_action(context)

    if decision.kind == "finish":
        evidence = verify_acceptance(state)
        save_verification(state, evidence)

        if evidence.passed:
            status = "completed"
            break

        state.add_feedback(evidence)
        checkpoint(state)
        continue

    validation = validate_and_authorize(decision, state)
    if not validation.allowed:
        state.add_feedback(validation)
        checkpoint(state)
        if validation.requires_user:
            status = "awaiting_user"
            break
        continue

    call_id = record_pending_action(state, decision)
    observation = execute_with_limits(decision, call_id)
    record_result(state, call_id, observation)
    checkpoint(state)

return report(status, state)
~~~

这里最重要的不是循环语法，而是几个边界：

- 模型请求结束，不等于验收已经通过。
- 工具执行前，要检查参数和授权。
- 执行有步数、时间和成本限制。
- 关键状态需要保存。
- 等待人工输入、预算耗尽和真正完成，是不同结果。

真实系统还需要处理并发修改、取消传播、会话恢复、持久化失败，以及有副作用操作的去重与对账。

## 8. 容易踩的坑与设计取舍

**把全部业务逻辑写进 Prompt。**规则会越来越长，也难以稳定执行。固定校验应该尽量放在程序和工具边界中。

**工具越多越好。**功能重叠会增加选择困难，最好先提供职责清楚的最小工具集合。

**把对话历史当作全部状态。**上下文压缩后，重要信息可能丢失。验收条件、执行记录和工作产物应独立保存。

**对任何错误都重试。**参数错误和权限不足通常需要修正；有副作用的超时要先核对结果。

**用框架代替验收。**框架可以简化开发，但无法替你定义“什么才算完成”。

Harness 也有成本：开发与维护更复杂，多轮执行增加延迟，持久化和观测需要基础设施，过于僵硬的流程还可能限制模型有效探索。

因此，单次分类、固定字段提取或简单生成任务，通常不需要复杂 Harness。对于步骤不确定、多工具交互、跨会话工作、需要可恢复状态的任务，它才更有价值。

## 9. 如何开始搭建？

建议从一条可验证的最小闭环开始：

1. 选择边界清晰的任务，先写验收条件。
2. 配置少量工具、参数校验和执行权限。
3. 建立基本循环，加入预算、超时和停止条件。
4. 保存任务状态、工具结果与关键产物。
5. 用真实案例评估完成率、恢复成功率、成本和耗时。
6. 根据反复出现的失败，再增加检索、压缩或更复杂的编排。

重点不是一开始设计“全能自主系统”，而是找到明确的失败模式，并逐个把它们变成可处理的工程问题。

## 10. 结语

理解 Harness，可以帮助我们把注意力从“模型能否给出聪明回答”，转向“系统能否可靠交付”。

模型影响理解和决策能力，Harness 负责组织环境、执行和反馈。它不会让模型永远正确，但可以让错误更容易被发现，让中断后的工作能够继续，让“完成任务”拥有可以检查的依据。

对于准备把 Agent 用到真实业务中的开发者来说，这些能力往往和模型选型同样重要。
